## 1. Summary

1. One Railway service: Fastify 5 + `@fastify/websocket` 11 serves the PWA (static), `/api/*` and `/ws` on one origin; Postgres through `pg` + drizzle-orm; no Redis, no worker process.
2. One WebSocket per device (phone or agent), authenticated before the upgrade; in-memory hub `userId -> Map<deviceId, connection>`; the relay routes opaque envelopes by `to` and derives presence from hub membership.
3. Delivery is at-least-once with idempotent receivers: every envelope carries `id` (UUIDv7), `seq` per `(from, session)`, `ts`, `expiresAt`; the relay writes every data envelope to a Postgres `outbox`, forwards it, deletes the row on the recipient's `ack`, and drains the outbox in `seq` order on reconnect.
4. Permission requests fail closed: the agent answers `deny` itself when no verified decision has arrived before `expiresAt` (set below the hook timeout) or when the relay is unreachable; the hook is configured with `onFailure: "block"`.
5. Postgres holds metadata plus short-lived ciphertext in `outbox`: `users`, `webauthn_credentials`, `devices`, `push_subscriptions`, `outbox`, `audit_log`; schema in drizzle, SQL migrations generated by `drizzle-kit generate`, applied by the relay at boot.
6. `packages/protocol` is zod 4 (the owner's kiko choice; `fastify-type-provider-zod` 7 for routes); `v` on every envelope, `hello` negotiation, additive-only changes, no codegen.
7. Graceful shutdown: SIGTERM -> `preClose` closes every socket with 1012 -> `fastify.close()` -> `pool.end()`; Railway `drainingSeconds` 15 and `overlapSeconds` 20.
8. Single replica for the MVP (Railway has no sticky sessions); the hub sits behind a port so a second replica can later fan out with Postgres LISTEN/NOTIFY — Redis is not needed.
9. Web Push via `web-push` (VAPID) carries only `{pending, requestId, deviceName, expiresAt}`; the PWA fetches the encrypted envelope over the WebSocket/outbox.
10. Layout: pnpm monorepo `apps/relay`, `apps/agent`, `apps/web`, `packages/protocol`, `packages/crypto`, `packages/test-fixtures`; tsconfig project references copied from agenthropic; vitest 5; TypeScript pinned to 6.x until typescript-eslint runs natively on 7.

## 3. Assumptions

- A1. What happens when a `PermissionRequest` hook times out is not stated explicitly in the hooks docs (F23 says "most events"). The design never relies on it: the agent always answers before the hook timeout. Report 04 should confirm.
- A2. Mobile carriers and home NAT drop idle TCP flows after roughly 30–120 s; Railway's WS exemption (F14) does not help there, hence 25 s heartbeats.
- A3. Typical payload sizes: a permission request (`tool_input`) is a few KB; a `PostToolUse` diff can be tens of KB. The agent truncates or chunks anything above 192 KiB of ciphertext (interface to reports 02/04).
- A4. Load for the first year: tens of users, 2–4 devices each, a few hundred envelopes per user per day. One Railway replica at 0.5 GB RAM is sufficient (each idle `ws` connection costs tens of KB).
- A5. The security report defines the payload format and keys. I assume: the relay sees the envelope header only, the payload is an AEAD ciphertext in base64, and the phone's decision inside the payload is bound to the request id and signed/authenticated so the agent, not the relay, is the party that verifies it.
- A6. The agent runs on Node 22 via `npx` and is online most of the time; the owner's machine sleeps at night (so "agent offline" is a normal state, not an error).
- A7. `drizzle-kit` 0.31.x is compatible with `drizzle-orm` 0.45.x (same release train; not executed here). drizzle's runtime `migrate()` is not safe to run concurrently from two instances without an advisory lock (not verified; mitigated in §5.9).
- A8. `uuid` 14 exports `v7()` (added in uuid 10; only the RFC 9562 self-description was verified, F4).
- A9. Clocks on phone and agent may skew by minutes. All expiries are compared against relay time (`relayTs` stamped on receipt); the agent uses a monotonic timer for the hook deadline.
- A10. Browser WebSocket clients cannot send protocol-level ping frames, so the PWA sends an application-level `ping` message; the Node agent can use `ws` ping frames.
- A11. The `@fastify/websocket` 11.x line targets Fastify 5 (devDependency and `fastify-plugin ^6`, F1/F10); no compatibility table exists to cite.

## 4. Findings

Hypotheses from brief §4 in my domain:

## 5. Recommendations

### 5.1 Relay runtime: Fastify 5 + `@fastify/websocket`

Register `@fastify/websocket` with `{ maxPayload: 262144, perMessageDeflate: false, clientTracking: false }` and a `preClose` hook (§5.13). Encrypted payloads do not compress, so deflate only costs CPU; 256 KiB caps a frame at the largest allowed envelope (A3). Route: `GET /ws` with `{ websocket: true }` and a `preValidation` hook that authenticates and attaches `{ userId, deviceId, kind }` to the request before the upgrade; failures reply 401 as plain HTTP, so unauthenticated clients never get a socket.

Authentication at upgrade: the PWA uses the same-origin session cookie (browsers cannot set headers on WebSocket requests); the agent sends `Authorization: Bearer <device token>` (Node `ws` client supports headers). The token format and the cookie policy belong to report 02; the relay stores only `devices.token_hash`.

Alternatives: raw `ws` with `noServer` on `http.createServer` — loses Fastify's hooks, logging and the plugin lifecycle, gains nothing; Socket.IO — adds a second protocol, fallback transports and larger client bundle for no benefit (every client here is a modern browser or Node); uWebSockets.js — native binary outside npm, overkill at this scale; Server-Sent Events + POST — would work for the phone but not for the agent (bidirectional, long-lived) and would double the transport code.

### 5.2 Hub and presence

`LocalHub` keeps `Map<userId, Map<deviceId, Conn>>` where `Conn = { socket, deviceId, kind, lastPong, bucket }`. On join/leave the relay sends `presence` to every other socket of the same user: `{ deviceId, online, at }` plus a full `presence` snapshot in `hello_ok`. `devices.last_seen_at` is written on connect, on disconnect and at most once per 60 s while connected (heartbeat-driven, throttled to keep writes trivial). The hub is defined as a port (`HubPort`: `attach`, `detach`, `sockets(userId)`, `send(deviceId, frame)`), so §5.14 can swap it.

### 5.3 Heartbeats

Relay -> every socket: `ws` ping every 25 s; if no pong within 10 s, `terminate()`. PWA -> relay: application-level `{"kind":"ping"}` every 25 s while the page is visible (A10); the relay answers `pong`. Agent -> relay: `ws` ping every 25 s, reconnect on missed pong. Rationale: Railway exempts WebSockets (F14) but NAT does not (A2); 25 s stays under typical NAT timers with margin and is a few bytes per device per half-minute.

### 5.4 Backpressure and abuse limits

- Outbound: `send(frame, cb)`; a frame counts as "sent" only when `cb` fires without error. Before draining the outbox for a socket, check `socket.bufferedAmount`; above 1 MiB, pause draining for that socket and retry on the next tick after the pending callbacks fire; above 4 MiB, close with 1013 (`try again later`) — the outbox keeps the rows, nothing is lost.
- Inbound: token bucket per connection (20 frames/s, burst 50); on overflow close 1008 (`policy violation`) and log at `warn`. `maxPayload` makes `ws` close with 1009 on oversized frames.
- HTTP: `@fastify/rate-limit` on `/api/auth/*` and `/api/pair/*` (policy numbers from report 02). Max 10 devices per user, enforced at pairing.

### 5.5 Envelope schema (`packages/protocol`)

```ts
// packages/protocol/src/v1.ts  (zod 4; the relay validates every inbound frame)
import { z } from "zod";

export const PROTOCOL_VERSION = 1;
export const DeviceId = z.uuid();
export const EnvelopeId = z.uuidv7();

// Data envelope: payload is opaque to the relay; everything else is routing metadata.
export const Envelope = z.object({
  v: z.literal(PROTOCOL_VERSION),
  kind: z.literal("data"),
  id: EnvelopeId,                       // sender-generated UUIDv7; dedup key (from, id)
  from: DeviceId,
  to: DeviceId.nullable(),              // null = all other devices of the same user (fan-out)
  session: z.string().max(128).nullable(), // agent session id (Claude Code session_id) or null
  cls: z.enum(["request", "reply", "event", "command"]),
  seq: z.int().nonnegative(),           // monotonic per (from, session); relay delivers in seq order
  ts: z.int(),                          // sender epoch ms (informational)
  expiresAt: z.int().nullable(),        // epoch ms; relay drops and never delivers after this
  replyTo: EnvelopeId.nullable(),       // for cls=reply: the request id
  payload: z.base64().max(262144),      // AEAD ciphertext (format: report 02)
});

// Control frames: plaintext, terminated by the relay.
export const Hello = z.object({ v: z.literal(1), kind: z.literal("hello"),
  protocol: z.object({ min: z.int().positive(), max: z.int().positive() }),
  resume: z.array(z.object({ session: z.string().nullable(), seq: z.int() })) });
export const HelloOk = z.object({ v: z.literal(1), kind: z.literal("hello_ok"),
  protocol: z.int(), deviceId: DeviceId, relayTs: z.int(),
  presence: z.array(z.object({ deviceId: DeviceId, kind: z.enum(["phone", "agent"]),
    name: z.string(), online: z.boolean(), lastSeen: z.int().nullable() })) });
export const Ack = z.object({ v: z.literal(1), kind: z.literal("ack"), ids: z.array(EnvelopeId).max(100) });
export const Presence = z.object({ v: z.literal(1), kind: z.literal("presence"),
  deviceId: DeviceId, online: z.boolean(), at: z.int() });
export const Ping = z.object({ v: z.literal(1), kind: z.literal("ping"), t: z.int() });
export const Pong = z.object({ v: z.literal(1), kind: z.literal("pong"), t: z.int(), relayTs: z.int() });
export const RelayError = z.object({ v: z.literal(1), kind: z.literal("error"),
  code: z.enum(["bad_frame", "unknown_device", "expired", "rate_limited", "unsupported_version"]),
  ref: EnvelopeId.nullable(), message: z.string().max(200) });

export const Frame = z.discriminatedUnion("kind", [Envelope, Hello, HelloOk, Ack, Presence, Ping, Pong, RelayError]);
export type Envelope = z.infer<typeof Envelope>;
export type Frame = z.infer<typeof Frame>;
```

Rules: the relay rejects a `data` frame whose `from` is not the authenticated device; `to` must belong to the same user (checked against `devices`); the relay stamps `relayTs` into the outbox row and uses it, not `ts`, for expiry. Receivers parse with `Frame` and ignore unknown `kind`s in later minor versions (`z.looseObject` on the receiving side).

### 5.6 Delivery semantics

Model: at-least-once, idempotent receivers, per-`(from, session)` ordering, no cross-session ordering.

- Sender keeps unacked envelopes in memory and resends them (same `id`) on reconnect. The agent's memory outbox is enough: a permission request that the agent cannot deliver before `expiresAt` is answered `deny` anyway (§5.6 case 1), and events are regenerable from the transcript.
- Relay: `INSERT outbox` -> forward to the live socket(s) -> on `ack` from the recipient, `DELETE`. Rows the recipient never acks are retried on its next `hello`, ordered by `(session, seq)`; a row past `expires_at` is deleted by the sweeper and never forwarded. Write-then-forward costs one insert and one delete per envelope; "forward first, persist only if offline" was rejected because a relay crash between forward and ack loses the message.
- Receiver dedup: a bounded LRU of `(from, id)` (last 1000 per peer) plus, for requests, the natural key "pending request with this id already exists". Duplicates are acked again and ignored.
- Reconnect: the client's `hello.resume` lists the highest `seq` it has seen per session; the relay drains outbox rows with `seq` above that and additionally everything with `delivered_at IS NULL` (so a forgotten ack is retried, not lost). `expiresAt` is evaluated against relay time at drain.

Case table for the blocking permission request (phone P, relay R, agent A):

| # | Situation | Behaviour |
|---|-----------|-----------|
| 1 | A running, R unreachable when Claude asks | A holds the hook, reconnects with backoff until `deadline = hookTimeout − 30 s`; at the deadline A answers `deny` with `message: "remote-control: no decision before deadline"`, `interrupt: false`. Claude sees an ordinary denial; the user can re-run from the terminal or phone. |
| 2 | A not running (daemon dead) | The `http` hook fails -> `onFailure: "block"` denies (F23). Fail closed by Claude Code itself. |
| 3 | P offline when the request arrives | R stores the row, sends Web Push (§5.16). When P connects, R drains; P shows the request if `expiresAt` is in the future, else "expired" (no decision possible). A denies at its own deadline. |
| 4 | P decides after `expiresAt` | R drops the reply (`error: expired`) if the row is already past expiry; otherwise A receives it, finds no pending request, replies `error: expired` to P. |
| 5 | P and A both reconnect | Each drains its outbox in `seq` order; A may receive the same decision twice -> first wins, later copies acked and ignored. |
| 6 | Two phones | `to: null` fans out to all phone devices; the first decision A accepts wins; A emits an `event` `resolved` so the other phone dismisses the card. |
| 7 | R restarts mid-flight | Unacked frames are re-sent by the sender; rows already in `outbox` are delivered after boot; the hub is rebuilt from new connections. |
| 8 | Claude Code hook timeout hits | Never by design: A's deadline is below the hook timeout (A1). |

Why deny-by-timeout rather than "no decision": a hook that returns nothing falls back to the normal permission flow (F23), which in an interactive terminal means a prompt nobody is looking at and in a non-interactive session means a denial anyway. An explicit deny is deterministic across both, is logged with a reason, and matches the brief's constraint that nothing runs without a decision bound to an authenticated device. Owner may enable fall-through later (§8 Q1). `AskUserQuestion` answers follow the same path with `cls: "reply"`.

### 5.7 Outbox retention and limits

- `cls = request/reply/command`: live until `expires_at` (set by the sender; relay caps at 15 min).
- `cls = event`: `expires_at` defaults to 1 h; events older than that are useless on a phone screen.
- Sweeper every 60 s: `DELETE FROM outbox WHERE expires_at < now() OR created_at < now() - interval '24 hours'`.
- Per-user cap 2000 rows / 20 MB; when exceeded the oldest `event` rows are deleted first; `request` rows are never evicted by the cap.
- Everything deleted is gone; the audit log keeps the metadata (`request_delivered`, `request_expired`) without payloads.

### 5.9 Database access and migrations

`pg.Pool` (`max: 5`, pool `'error'` listener, F26) wrapped by `drizzle-orm/node-postgres` (F27). Schema in TypeScript (`apps/relay/src/db/schema.ts`), `pnpm --filter relay db:generate` produces committed SQL under `apps/relay/drizzle/`; the relay runs `migrate()` at boot, inside `SELECT pg_advisory_lock(<constant>)` on a dedicated client, before `listen()` (A7). Railway's `preDeployCommand` is the alternative hook if report 06 prefers it; both are idempotent.

Alternatives: node-pg-migrate — solid, but a second DSL next to the query layer; kysely — typed query builder without schema diffing, so migrations are hand-written; raw SQL + a 40-line runner — fine, but drizzle gives typed queries for free and the owner already knows it from kiko; `drizzle-kit push` — no history, rejected for anything past a local sandbox; Prisma — a second runtime and a binary engine for six tables.

### 5.10 Protocol package and versioning

- zod 4 everywhere (F29); `fastify-type-provider-zod` 7 for route schemas and OpenAPI-free validation (F3). `zod/mini` for `apps/web` only if the bundle ever matters (F29 says it rarely does).
- Versioning: `v` on every frame; `hello.protocol = { min, max }`; the relay answers `hello_ok.protocol` with the highest version both support or closes with 4001 `unsupported_version` (the agent prints "update: npx remote-control@latest"). The relay supports the current and the previous major. Inside a major, changes are additive only: new optional fields, new `kind`s/`cls` values that old receivers ignore. The encrypted payload has its own inner `pv` header negotiated phone <-> agent through the same `hello` mechanism relayed as an `event` (reports 02/04 own the inner format).
- No codegen: both ends are TypeScript and import `packages/protocol`; `z.infer` provides the types. Generate JSON Schema (`z.toJSONSchema`) only for documentation if a non-TS adapter ever appears.

Alternatives: TypeBox — JSON Schema first, which matters when schemas are shared with non-TS consumers; here they are not, and the 1.x package move (F30) adds churn; protobuf/CBOR — binary framing is not needed for KB-sized envelopes and would complicate debugging in the browser.

### 5.11 One origin: static PWA + API + WS

`@fastify/static` with `root: apps/relay/public`, `prefix: "/"`, `wildcard: false`; a `setNotFoundHandler` that returns `index.html` (`maxAge: 0`) for `GET` requests whose `Accept` includes `text/html` and whose path is not under `/api` or `/ws`, otherwise a JSON 404 (F13). Hashed Vite assets under `/assets/` get `maxAge: 1y, immutable`; `index.html`, `sw.js` and `manifest.webmanifest` get `no-cache`. The Docker build runs `vite build` and copies `apps/web/dist` into `apps/relay/public`. Dev: Vite dev server proxies `/api` and `/ws` to the relay on `localhost:3000`.

Alternative: a second Railway service or a static host for the PWA — a second origin means CORS, `SameSite=None` cookies, a WebAuthn RP ID that no longer matches the API host, and two deploys to keep in sync. Rejected for the MVP; nothing in the single-origin design blocks splitting later.

### 5.12 Health endpoint

`GET /health` -> `200 { status: "ok", version: RAILWAY_GIT_COMMIT_SHA, uptimeSec, db: "ok" }` after `SELECT 1` with a 2 s timeout; `503 { status: "degraded", db: "error" }` if the pool fails; after `close()` Fastify answers 503 by itself. Logging at `trace` for that route (the deploy check and any uptime pinger would otherwise fill the logs). `@fastify/under-pressure` is not needed for the MVP; add it only if memory limits bite (F20).

### 5.13 Graceful shutdown and Railway timing

```
SIGTERM/SIGINT (once) -> shuttingDown = true
  -> fastify.close():
       preClose: for each hub socket: socket.close(1012, "service restart"); hub.clear()
       (Fastify stops listening, waits for in-flight HTTP)
       onClose: await pool.end(); await notifyClient.end()   // §5.14
  -> process.exit(0); a 10 s fallback timer calls process.exit(1)
```

`preClose` is mandatory: Fastify does not track upgraded sockets (F12). Code 1012 tells clients to reconnect immediately with jitter (0–3 s) instead of backoff, so a redeploy costs one reconnect. Railway settings needed from report 06: `drainingSeconds: 15`, `overlapSeconds: 20`, `healthcheckPath: /health`, `healthcheckTimeout: 100`, `restartPolicyType: ON_FAILURE`, `numReplicas: 1` (F16–F18); the mechanism (settings UI vs. IaC) is theirs because `railway.json` expires on 2026-12-01 (F17).

### 5.14 Scaling beyond one replica

Not for the MVP (F19, F20, A4). The design already makes it a small step: every envelope goes through `outbox`, so a `PgNotifyHub` can replace `LocalHub` without touching the protocol — each replica `LISTEN rc_outbox` on a dedicated `pg.Client` (F26); after `INSERT outbox` the writer does `NOTIFY rc_outbox, '<to_device_id>'` (36 bytes, far under 8000, F24); the replica that holds that device's socket claims rows with `SELECT ... FOR UPDATE SKIP LOCKED` (F25) and forwards them; presence is read from `devices.last_seen_at` instead of hub memory. Redis pub/sub is the alternative if NOTIFY throughput or the one-LISTEN-connection-per-replica ever limits; at this scale it is a second service for nothing. Sticky sessions are not available on Railway, so an external load balancer was also considered and rejected (cost, ops).

### 5.16 Web Push

`PushPort.notifyPending(deviceId, { requestId, deviceName, expiresAt })` implemented with `web-push` (F31): payload `{"t":"pending","rid":"<id>","dev":"<agent name>","exp":<epoch ms>}` (< 200 bytes, under the 4096-byte floor, F32), `topic: rid without hyphens` (32 chars, so a re-sent request replaces its own notification), `urgency: "high"`, `TTL: max(0, ceil((expiresAt − now) / 1000))` so an expired request never buzzes a phone. Sent for every `cls: "request"` envelope to each phone device of the user that has not acked within 3 s (a backgrounded PWA may hold a suspended socket). 404/410 delete the subscription; 429/5xx set `last_failure` and are not retried in the MVP. VAPID keys come from env (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`). The PWA never trusts the push body: it opens, connects, drains the outbox, and renders what it decrypts.

### 5.17 Observability (minimum)

pino via Fastify with `redact` for `authorization`, cookies and `push_subscriptions.endpoint`; one structured log line per envelope with `id`, `cls`, `bytes`, `from`, `to`, never `payload`. Counters in memory exposed at `GET /metrics` (plain JSON, admin-token protected) for sockets, envelopes/min, outbox rows, push results; report 06 decides whether anything scrapes it.

## 8. Open questions for the owner

1. **Deadline behaviour**: explicit `deny` (proposed default) or fall through to the terminal prompt when no decision arrives? Default: deny; add an agent flag `--on-timeout=fallthrough` later if terminal use suffers.
2. **Request lifetime**: hook `timeout` 600 s (Claude Code default) with the agent deadline at 570 s, i.e. about 9.5 min to answer from the phone. Default: keep 600/570; make the hook timeout the single knob.
3. **Ciphertext at rest in `outbox`** for up to the envelope lifetime (minutes for requests, 1 h for events, 24 h hard cap). Default: accept and state it in the privacy text as "stores encrypted messages it cannot read until delivered or expired".
4. **Railway plan**: Free (0.5 GB, 1 replica, $1 credit) or Hobby ($5). Default: Hobby once Postgres is attached; report 06 confirms.
5. **Account identifier**: email (recovery possible, PII stored) vs. username-only. Default: email; report 02 may override.
